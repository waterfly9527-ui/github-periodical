四层项目版图

从声明到消费，越往右越接近开发者体验；越往左越接近系统约束与真实资源。

01 · 定义层

CUE + OpenTofu

把配置、约束和基础设施期望状态变成可审查、可版本化的声明。

02 · 控制面

Crossplane + Argo CD

持续比较“期望状态”与“真实状态”，并通过 reconciliation/GitOps 收敛偏差。

03 · 执行层

Dagger + Temporal

一个解决可移植软件交付执行，一个解决长生命周期、失败可恢复的业务/基础设施工作流。

04 · 入口层

Backstage

把底层复杂度封装成目录、模板和自助入口，让平台能力变成团队可消费产品。

关键变化

GitHub 事实
  • Argo CD、Crossplane、Temporal 在 2026-08-09 仍有代码 push；Dagger 在 08-08，OpenTofu 与 Backstage 在 08-07，CUE 在 08-05。
  • 这些项目都把声明式、工作流、控制平面、GitOps、自助门户或配置验证作为核心能力。
  • 7 个仓库合计超过 14 万 Stars，且都不是一次性 demo，而是长期维护的基础设施项目。
编辑分析
  • 声明式已经从 Kubernetes YAML 扩展到 IaC、软件交付、业务工作流和开发者门户。
  • “持续收敛”比“一次执行成功”更重要：系统要能检测漂移、恢复失败并保留审计链。
  • 平台团队真正的产品不再是脚本仓库，而是有类型、有策略、有入口的内部控制面。

风险矩阵

抽象叠加

同时引入 IaC、Kubernetes 控制器、GitOps、工作流和门户，会增加学习面与故障边界。先定义边界，再选工具。

状态所有权冲突

OpenTofu、Crossplane、Argo CD 都可能“拥有”某些资源。必须明确单一 source of truth，避免双控制器争抢。

平台产品化成本

Backstage 等入口只有在底层 API、模板和权限模型稳定后才有价值；过早做门户会把混乱包装得更漂亮。

团队采用路径

1先规范声明

用 CUE 或现有 schema 工具建立配置约束；IaC 场景用 OpenTofu 固化资源生命周期和 plan/apply 审核。

2再引入收敛

Kubernetes 侧使用 Argo CD 管应用状态；需要把云资源变成 Kubernetes API 时再评估 Crossplane。

3最后产品化

用 Dagger/Temporal 承载可复用执行，再通过 Backstage 模板和目录把能力开放给开发团队。
