WASM 正在成为插件、边缘
与 Agent 工具的通用沙箱

本期不讨论“WebAssembly 会不会替代容器”，而是看一个更具体的变化：运行时、WIT/Component Model、插件框架和 MCP 工具开始拼成同一条工程链路，让第三方代码可以跨语言运行，同时把文件、网络、凭证和宿主函数收进显式能力边界。

9 个项目4 层技术版图事实仅来自 GitHubStars/Forks 为生成时快照
编辑判断：Wasm 的新价值不在“更小的容器”，而在“更强的宿主控制”。当接口由 WIT 描述、组件只拿到被授权能力时，插件、Agent 工具和边缘函数可以共享一套更可审计的执行模型。

四层项目版图

从最底层的执行引擎，到最上层真正承载插件、Agent 工具和分布式服务的平台。

01 运行时与隔离Wasmtime / Wasmer：负责加载、编译、实例化、资源限制和宿主能力。
02 Component 工具链wasm-tools / wit-bindgen / jco：定义接口、生成绑定、转换与检查组件。
03 插件与 Agent 工具Extism / Wassette：把 Wasm 变成产品插件或 MCP 工具沙箱。
04 Serverless / EdgeSpin / wasmCloud：把组件提升为可部署、可伸缩、可跨环境运行的服务单元。

团队采用路径

不是所有团队都需要 wasmCloud，也不是所有插件系统都要自己嵌 Wasmtime。按问题选层级。

已有产品要支持第三方插件
Extism → 必要时下沉 Wasmtime。先拿到插件 SDK、多语言 Guest 和宿主 API，再决定是否自己管理 runtime。
要建立跨语言稳定 ABI
WIT + wit-bindgen + wasm-tools。把接口定义和兼容检查放进源码与 CI，而不是继续堆手写 C ABI。
Agent / MCP 工具需要隔离
Wassette + OCI 组件白名单。重点不是“能加载工具”，而是把文件、网络和凭证权限做成显式能力。
轻量 HTTP / 事件服务
Spin。它已经把构建、运行、分发和 Component Model 串成较完整的开发体验。
跨云、K8s、边缘调度组件
wasmCloud。只有当需求越过单机 runtime、需要能力链接和分布式调度时再承担平台复杂度。
需要自己的底层执行引擎
Wasmtime / Wasmer。适合需要直接控制内存、燃料、epoch、宿主函数和嵌入 API 的基础设施团队。

四个必须提前处理的风险

能力泄漏
Wasm 内存隔离不等于安全完成。宿主暴露的文件、网络、环境变量、密钥和回调函数才是实际攻击面。
标准仍在演进
Component Model、WASI Preview3 与相关工具链持续变化。必须锁版本、版本化 WIT，并建立跨版本兼容测试。
错误迁移目标
把普通长生命周期容器机械改成 Wasm 通常收益有限。插件、短任务、边缘函数和受限 Agent 工具更容易先得到净收益。
调试与可观测性
多语言 Guest 并不会自动降低运维成本。栈追踪、日志、指标、性能分析和崩溃归因仍需要宿主平台补齐。
