eBPF 正在把可观测性
从 SDK 埋点推向内核级自动采集

本期关注一个已经从“高级内核技巧”进入平台工程主路径的变化：应用不改代码，也能先得到 traces、RED metrics、CPU profiles、网络拓扑甚至运行时安全事件。关键不在于 eBPF 替代 OpenTelemetry SDK，而在于它正在成为观测系统的自动 baseline。

本周关键 GitHub 变化：Grafana Beyla README 已明确宣布项目捐赠给 OpenTelemetry，并将主要开发迁移到 OpenTelemetry eBPF Instrumentation（OBI）。OBI 主仓库在 8 月 30 日仍持续更新。这意味着零代码 eBPF instrumentation 正从厂商项目向 OpenTelemetry 公共标准层收敛。

事实与编辑判断

GitHub 仓库事实

OBI 的仓库 description 是“Zero-code OpenTelemetry instrumentation powered by eBPF”；Beyla README 明确说明迁移；OpenTelemetry eBPF Profiler、Tetragon、DeepFlow 等仓库在 8 月 28–30 日仍有主分支 push。

编辑分析

平台团队更现实的路线不是“删除 SDK”，而是先用 eBPF 自动获得服务拓扑、基础 traces、RED metrics 与 profiles，再只对订单、用户、业务步骤等高价值语义补手工 instrumentation。

四层项目版图

01 零代码 InstrumentationOBI、Beyla：从进程与网络层自动生成 OpenTelemetry metrics / traces。
02 Continuous ProfilingOTel eBPF Profiler、Pyroscope、Parca：持续采 CPU/内存热点并跨版本、跨时间比较。
03 全栈 APMDeepFlow：把 eBPF tracing、profiling、网络可见性与 OpenTelemetry 放到一套平台里。
04 Runtime SecurityTetragon：同一类内核可见性进一步延伸到安全事件与运行时执行。

主要风险

权限与内核兼容

eBPF 通常需要 Linux 内核能力与额外 capabilities。Beyla README 明确列出 Linux/BTF/eBPF 和 elevated permissions 要求；生产铺开前必须做内核、BTF、容器权限矩阵。

自动采集 ≠ 业务语义

自动 traces 能看见 HTTP/gRPC/SQL 等调用，但订单号、租户、用户动作等业务上下文仍需 SDK 或显式上下文传播。

数据成本

持续 profiles 和全量 traces 容易快速放大存储与查询成本。必须提前制定采样、retention、cardinality 与标签规范。

许可证边界

Pyroscope 为 AGPL-3.0；其余本期核心项目多为 Apache-2.0。嵌入、修改和对外提供服务前应分别核对义务。

团队采用路径

已有 OpenTelemetry

先在一个非关键 Kubernetes namespace 部署 OBI，拿到自动 baseline；保留已有 SDK 负责业务 spans 与高价值 attributes。

还没有统一 APM

用 Beyla/OBI 或 DeepFlow 先验证“无需改代码”的服务拓扑、RED metrics 和 traces，再决定后端存储与 UI。

CPU / 成本优化优先

用 OpenTelemetry eBPF Profiler 作为采集入口，再在 Pyroscope 或 Parca 中做 flame graph、版本对比与长期分析。

Kubernetes 安全团队

Tetragon 单独作为运行时安全数据平面；权限、保留策略和告警流程不要与 APM 数据直接混用。

仓库事实仅来自 GitHub 仓库主页、README、Topics、License 与仓库活动字段；趋势判断、风险与采用路径属于编辑分析。
